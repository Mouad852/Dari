### Test suite

- [x] **Fixed 2026-09-08 — the coordinate half of the flakiness.** `ListingApiTest.publicDetailIsVisibleForPublishedListing` and `FavoriteApiTest.addListAndRemoveFavorite` asserted the response did *not contain* a substring of the unfuzzed coordinate (e.g. `"longitude":-6.8498`). But `LocationFuzzer` derives its offset from the listing's UUID, random per run, so whenever the offset landed small the fuzzed value simply *started with* the original's digits (`-6.8498` → `-6.8498304629046105`) and the substring check tripped. Never a data-isolation problem. Both now compare numerically against `LocationFuzzer.fuzz(...)`'s own output, which is deterministic given the id, so offset size cannot affect the result. Two things fell out of the fix: a new `LocationFuzzerTest` covering the fuzzer's own guarantees (determinism, that the point always moves, and that 1,000 sampled offsets all stay inside the 200m radius) — it had **no test at all** before, which is why these API tests were left guessing at digit prefixes; and `AbstractIntegrationTest.exactNumbers()`, because RestAssured parses JSON numbers as **float** by default, which holds ~7 significant digits and silently shifted the eighth by ~1e-6. Verified with 5 consecutive clean runs, not one.
- [x] **Fixed 2026-09-08 — and it was never actually the shared-container isolation problem this was filed under.** `ListingSearchOptimizationTest.distanceSortWorks` has its own `@BeforeEach` that deletes every `PUBLISHED`/`AVAILABLE` listing before each test and JUnit runs this suite sequentially (no parallel execution configured), so cross-class data leakage was never possible for this test — that theory didn't survive checking. The real cause: `listings.location` is a `geography(Point,4326)` column, so the query's `ORDER BY ST_Distance(...)` sorts using PostGIS's geodesic (WGS84 spheroid) distance, while the test re-verified the order using its own `haversineMiles` helper — a spherical-Earth approximation. The two models disagree by a few metres for two listings that land nearly equidistant from the search origin (10 listings scattered randomly within ~15km each run), which was occasionally enough to flip their apparent relative order and fail a strict `>=` assertion — a real disagreement between two distance formulas, not a bug in the query, the pagination, or test isolation. Fixed by asserting against `ST_Distance` itself (queried directly via `JdbcTemplate`, the exact computation the query ordered by) instead of a Java reimplementation of it — removes the discrepancy at the root rather than tolerating it with an epsilon. Verified with 8 consecutive clean runs across different random seedings, not one.

Fixed by capping `mapPinsByLocationAndRadius` at 1,000 rows (ordered by recency); the identical rerun measured p95 201ms for map, and every other endpoint improved too (search 606ms → 177ms, radius 659ms → 230ms, count 410ms → 122ms; throughput 136 → 355 req/s) since the one unbounded endpoint had been starving connection-pool/CPU capacity under concurrent load. Error rate was 0% throughout — this was a latency/payload problem, not a correctness one. Full methodology, before/after table, and recorded acceptance thresholds are in `docs/PRODUCTION_OPERATIONS.md`'s new "Search load testing" section; the thresholds are also encoded directly in the k6 script so a future regression run fails loudly.
